## ゴール（社長の狙い）
アド・クリックス様のスプレッドシートで「コール状況」列に「資料請求」または「資料送付」が入力されたら、その行の情報を通知する。**アポインターが獲得した資料送付を、クライアント様へ確実に報告し、報告漏れを防ぐ**のが目的。

## 確定している決定事項（Q1〜Q4）
- **Q1**：トリガーキーワード＝「資料請求」「資料送付」の**両方**
- **Q2**：LINE の Messaging API は**未設定**（→ LINE は後回し。まずメール＋Slack を動かす2段構え）
- **Q3**：**出し分け**。LINE＝企業名・住所・電話番号だけ（クライアント向けにスッキリ）／メール・Slack＝＋シート名・行番号（社内の追跡用）
- **Q4**：対象は**アド・クリックス様のみ**。監視シートは「リスト（寺社仏閣）」「リスト（社福）」

## 届け先の意図（最重要・誤爆厳禁）
LINE の最終的な届け先は、**クライアント様と繋がっている add one 公式LINEのグループチャット**（特定グループへの push）。一斉配信（ブロードキャスト）は**絶対に使わない**。お客さんに社内情報が飛ぶ事故を構造的に防ぐこと。

## ★既存スクリプトとの衝突チェック（デスクトップで最初にやること）
このスクリプトの編集監視関数は、**あえて `onEdit` ではなく `onResourceRequestEdit` という独自名**にしてあり、**インストール型トリガー（`setupTrigger`）**で起動する設計です。
→ だから**既存の `onEdit` とはぶつかりません**（ここが一番の安全ポイント）。メール送信・外部通知にはどのみちインストール型トリガーが必要なので、この作りが正解です。

ただし、以下の**汎用的な名前**は既存スクリプトとかぶる可能性があるので、貼る前に既存2本を画面で確認：
- `CONFIG` / `setupTrigger` / `testNotify`

かぶっていたら、こちら側の名前を変える（例：`CONFIG_RR` / `setupTrigger_RR` / `testNotify_RR`）か、1ファイルに統合する。画面操作版なら、既存スクリプトを画面で読んでその場で判断・修正できます。

## 画面操作で進めるときの流れ
1. **社長がスプシにログイン**し、「拡張機能 → Apps Script」を開く（ログインは社長の手で）
2. デスクトップ Claude が既存スクリプトを画面で読み、上の衝突チェック
3. 新規ファイルとしてコードを貼る → CONFIG を埋める
4. **秘密情報（Slack Webhook URL・LINE アクセストークン等）の入力は社長の手で**（Claude に預けない）
5. `setupTrigger` を実行 → **認可画面の承認は社長の手で**
6. `testNotify` で動作確認 → メール・Slack が届けば成功
